# Единый технический контекст проекта PQlocalAgentOS v3

## Для DeepSeek и ChatGPT

### 1. Назначение документа

Этот документ синхронизирует понимание проекта между DeepSeek и ChatGPT.

**Репозиторий:** [https://github.com/alexpikman/PQlocalAgentOSv3](https://github.com/alexpikman/PQlocalAgentOSv3)

**Основная ветка:** `main`

**Регламент совместной разработки:** [https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/PROCESS.md](https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/PROCESS.md)

**Правила репозитория:** [https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/AGENTS.md](https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/AGENTS.md)

**Входная точка технической документации:** [https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/docs/ai-context/README.md](https://github.com/alexpikman/PQlocalAgentOSv3/blob/main/docs/ai-context/README.md)

Документ является стартовым контекстом, а не заменой изучения исходников. Перед каждой задачей оба ИИ обязаны сверять сведения с актуальным состоянием репозитория.

### 2. Роли участников

**Пользователь — руководитель проекта.**

- Формулирует цели и требования.
- Передаёт промпты и ответы между DeepSeek и ChatGPT.
- Получает изменения через GitHub Desktop.
- Запускает приложение на своём ПК.
- Проверяет интерфейс и реальные пользовательские сценарии.
- Выносит окончательное решение: принято, требует исправлений или заблокировано.

**DeepSeek — аналитик и технический координатор.**

- Осмысляет идею пользователя с учётом текущего кода и конечной цели.
- Изучает техническую документацию и релевантные файлы.
- Формирует точное задание для ChatGPT в Markdown.
- Проверяет ответ ChatGPT на соответствие требованиям, ограничениям и архитектуре.
- Выявляет пропуски, потенциальные регрессии и неподтверждённые заявления.
- Формирует следующую итерацию, если задача не завершена.

**ChatGPT — разработчик.**

- Изучает актуальные файлы репозитория перед изменением.
- Определяет минимально необходимый объём изменений.
- Вносит изменения непосредственно в репозиторий, если доступ и инструменты позволяют это сделать.
- Работает исключительно в `main`, согласно `AGENTS.md` и `PROCESS.md`.
- Выполняет доступные проверки и фиксирует реальные результаты.
- Возвращает структурированный отчёт по шаблону из `PROCESS.md`.
- Не утверждает, что изменения закоммичены, тесты пройдены или приложение работает, если это не подтверждено.

**Пользователь — единственный канал обмена между ИИ.** История чатов DeepSeek и ChatGPT автоматически не синхронизируется. Важный контекст передаётся явно.

### 3. Что представляет собой проект

PQlocalAgentOS v3 — локальная веб-платформа для управления AI-агентами, моделями, проектами, задачами, настройками интерфейса и подключаемыми модулями.

Проект находится в активной разработке. Наличие элемента интерфейса, API или документации само по себе не доказывает завершённость соответствующей функции.

Основные технологии, подтверждённые структурой и исходниками:

- Python HTTP-сервер на базе `ThreadingHTTPServer` и `SimpleHTTPRequestHandler`.
- Статический frontend на HTML, CSS и Vanilla JavaScript.
- Локальные JSON-файлы и другие файловые механизмы хранения.
- Ollama для событийного чатового runtime.
- SSE для доставки событий чата и HTTP POST для команд.
- Python `unittest` для автоматических проверок.
- GitHub Actions для проверок при изменениях репозитория.

Точные зависимости и возможности конкретной функции нужно проверять в актуальных исходниках, `requirements.txt` и соответствующих тестах.

### 4. Архитектурная карта

**Сервер и API**

- `server.py` — точка входа приложения, HTTP-маршруты, API, статические файлы и интеграции.
- По умолчанию сервер использует `127.0.0.1:8765`.
- Порт можно переопределить переменной окружения `PQ_PORT`.

**Основной frontend**

- `frontend/app.js` — основная логика интерфейса, страниц, меню, настроек, сущностей и интеграций.
- `frontend/index.html` — основной HTML-каркас.
- `frontend/styles/` — разделённые слои CSS и визуальные токены.
- `frontend/domain-modal.js` — общая логика модальных окон доменных сущностей.

**Чат**

- `frontend/chat.js` — UI и взаимодействие с чатовым API.
- `frontend/chat-transport.js` — транспорт SSE и отправка команд.
- `frontend/chat-renderer.js` — отображение событий и результатов в DOM.
- `chat/agent_runtime.py` — выполнение хода агента и обработка инструментальных вызовов.
- `chat/conversation_store.py` — долговременный журнал диалогов и событий.
- `chat/chat_events.py` — EventHub для доставки событий подписчикам.
- `chat/provider_adapter.py` — адаптер провайдера.
- `agent_tools.py` — инструменты и проверки разрешений.

**Документация**

- `docs/ai-context/00-project-overview.md` — назначение и границы проекта.
- `docs/ai-context/01-architecture.md` — архитектура и потоки данных.
- `docs/ai-context/02-tech-stack.md` — технический стек.
- `docs/ai-context/03-glossary.md` — терминология.
- `docs/ai-context/modules/` — контракты отдельных компонентов.
- `docs/ai-context/tests/test-map.md` — карта автоматических тестов.
- `docs/MODULE_ARCHITECTURE.md` — архитектура модулей.
- `module-contract.schema.json` — схема контракта модуля.

### 5. Архитектурные инварианты

1. Источник истины — актуальная ветка `main` и фактические исходники.
2. Перед изменением читать целевой файл, связанные компоненты и тесты.
3. Предпочитать минимальные изменения вместо широкого рефакторинга без необходимости.
4. Не менять несвязанные части проекта.
5. При изменении API сохранять совместимость либо явно обосновывать и проверять её нарушение.
6. При изменении событий чата согласованно проверять runtime, Store, EventHub, frontend transport, renderer и тесты.
7. Не считать EventHub постоянным хранилищем: журнал событий находится в ConversationStore.
8. Запись события в журнал должна предшествовать публикации события подписчикам.
9. Не путать SSE с WebSocket.
10. Не считать основной runtime всех AI-агентов и runtime событийного чата одной системой.
11. Не считать общий каталог провайдеров доказательством поддержки всех форматов потоковым чатом.
12. Не считать наличие разрешений и ограниченных корней полноценной изоляцией на уровне операционной системы.
13. Не вставлять недоверенный пользовательский или модельный текст в HTML без безопасного экранирования или DOM API.
14. Не добавлять зависимости, новые архитектурные слои или новые механизмы хранения без обоснованной необходимости.

### 6. Известные ограничения

Эти ограничения следует повторно сверять с кодом перед каждой задачей:

- Событийный чат в `server.py` ориентирован на провайдера формата Ollama. Другие форматы нельзя считать поддерживаемыми без проверки.
- ConversationStore использует файловый журнал JSONL и блокировки внутри процесса; это не полноценная межпроцессная система транзакций.
- Дедупликация команд и реестр активных задач runtime хранятся в памяти процесса.
- Отмена задачи реализована через сигнал отмены, но завершённость всего пользовательского сценария отмены должна проверяться отдельно.
- Доступ к локальным файлам по умолчанию выключен и требует разрешённых корней и прав конкретного агента.
- Ограничения файловых инструментов не следует называть полноценным sandbox ОС.
- Добавление GitHub-репозитория в каталог не означает безопасную установку или выполнение внешнего кода.
- Наличие интерфейса провайдера или модели не гарантирует работоспособность реального подключения.
- Автоматические backend-тесты не подтверждают визуальную корректность интерфейса в браузере.
- Документация может отставать от реализации.

### 7. Тесты и проверка результата

Основные тестовые файлы:

- `tests/test_server.py`
- `tests/test_agent_tools.py`
- `tests/test_agent_runtime.py`
- `tests/test_chat_agent_runtime.py`
- `tests/test_conversation_store.py`

Команда запуска тестов в Windows PowerShell:

```powershell
python -m unittest discover -s tests -v
```

В репозитории также имеются GitHub Actions:

- `.github/workflows/tests.yml`
- `.github/workflows/chat-event-ci.yml`

Они предусматривают проверки Python, синтаксиса JavaScript, JSON-контракта, HTTP-поведения и unit-тестов.

Не заявлять об успешном выполнении этих проверок без фактического результата.

Проверки разделяются на три уровня:

1. **ChatGPT:** чтение и анализ кода, тесты, совместимость и потенциальные регрессии.
2. **DeepSeek:** независимая оценка решения относительно цели, архитектуры и ограничений.
3. **Пользователь:** обновление проекта через GitHub Desktop, реальный запуск и проверка в браузере.

### 8. Обязательная процедура разработки

1. Пользователь описывает идею или проблему.
2. DeepSeek уточняет цель, изучает контекст и формирует точный промпт для ChatGPT.
3. Пользователь передаёт промпт ChatGPT.
4. ChatGPT изучает актуальный код и выполняет работу в пределах доступных полномочий и инструментов.
5. ChatGPT возвращает отчёт по обязательному шаблону.
6. Пользователь пересылает отчёт DeepSeek.
7. DeepSeek проверяет полноту решения, соответствие требованиям и потенциальные ошибки.
8. При необходимости DeepSeek формирует корректирующий промпт.
9. Пользователь получает изменения через GitHub Desktop и проверяет приложение.
10. Пользователь определяет итоговый статус задачи.

### 9. Обязательный формат отчёта ChatGPT

Каждый ответ о выполненной разработке должен содержать следующие разделы:

1. **Что сделано** — конкретные изменения и их назначение.
2. **Изменённые файлы** — таблица файлов, изменений и причин.
3. **Код изменений** — существенные фрагменты или diff с указанием языка.
4. **Что проверено** — выполненные и невыполненные проверки с реальными результатами.
5. **Как проверить** — пошаговый сценарий для пользователя на ПК.
6. **Риски и ограничения** — допущения, возможные регрессии и непокрытые случаи.
7. **Коммит** — сообщение, ветка `main`, хэш и ссылка, если коммит действительно создан.

Если раздел неприменим, это нужно объяснить, а не пропускать молча.

### 10. Формат промпта DeepSeek для ChatGPT

Каждый промпт должен включать:

- Цель и наблюдаемую проблему.
- Текущее поведение и требуемое поведение.
- Релевантные файлы и документы для изучения.
- Обязательное требование проверить актуальную реализацию.
- Точный объём изменений.
- Что нельзя менять.
- Критерии приёмки.
- Требования к регрессионным тестам.
- Способы проверки и ограничения среды.
- Требование вернуть отчёт по семи разделам из `PROCESS.md`.

Не предполагать заранее, какой код нужно переписать, если ещё не исследована реализация.

### 11. Правила работы с GitHub

Согласно `AGENTS.md` и `PROCESS.md`:

- Работать только в ветке `main`.
- Не создавать отдельные рабочие ветки и pull request для обычных изменений.
- Перед редактированием читать актуальные файлы.
- Сохранять посторонние изменения.
- Для нескольких файлов соблюдать последовательность и не заменять новые версии файлов устаревшими копиями.
- После изменений проверять итоговое состояние `main` и запускать доступные тесты/CI.

Если у ChatGPT нет технической возможности внести изменения непосредственно в GitHub, необходимо честно сообщить об ограничении и предоставить точный diff или инструкцию. Нельзя выдавать подготовленный код за уже внесённый коммит.

### 12. Начало работы над каждой новой задачей

DeepSeek и ChatGPT должны определить:

1. Какой результат хочет получить пользователь.
2. Какие части системы затрагиваются.
3. Какие исходники и тесты нужно прочитать.
4. Какие существующие контракты и функции нельзя нарушить.
5. Как доказать выполнение задачи.
6. Какие проверки недоступны без локального запуска пользователя.

Если контекста недостаточно, запросить только действительно необходимые уточнения.

### 13. Итоговый принцип

**DeepSeek отвечает за техническую постановку задачи и независимую оценку ответа. ChatGPT отвечает за изучение исходников, реализацию и проверку кода. Пользователь отвечает за передачу контекста, локальный запуск и окончательную приёмку.**

Оба ИИ обязаны различать подтверждённые факты, предположения и планы. При расхождении мнений нужно сверяться с исходниками, тестами и критериями приёмки, а не выбирать ответ по уверенности формулировки.

Главная цель — последовательное развитие одного и того же проекта без потери контекста, случайного изменения архитектуры и неподтверждённых заявлений о готовности.
