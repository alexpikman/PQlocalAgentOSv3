# PQlocalAgentOS v3 — карта внутреннего управления задачами и взаимодействия AI-агентов

## 1. Назначение документа

Документ описывает внутренний процесс работы AI-агентов непосредственно в приложении PQlocalAgentOS v3: постановку и регистрацию задач, анализ требований, планирование, выбор исполнителей, передачу контекста, выполнение этапов, контроль качества, обработку ошибок и блокировок, прогресс проекта, хранение результатов и историю, а также разрешения на инструменты и потенциально опасные действия.

**Граница системы:** MANAGER, ANALYST, ARCHITECT, DESIGNER, CODER, TESTER, DEVOPS и COPYWRITER — внутренние роли приложения. Пользователь, DeepSeek и ChatGPT, участвующие во внешней разработке репозитория, в этот внутренний рабочий процесс не входят.

### Правило достоверности

- **Описано** — функция или правило присутствует в документации либо шаблоне агента.
- **Подтверждено кодом** — поведение найдено в реализации и, где необходимо, тестах.
- **Требует реализации или проверки** — описано желаемое поведение, но фактическая работа не подтверждена.

Нельзя выдавать предполагаемое поведение за готовую функцию.

## 2. Общая архитектурная карта внутренней системы

```text
ПОЛЬЗОВАТЕЛЬ В ПРИЛОЖЕНИИ
          |
          v
ПОСТАНОВКА ЗАДАЧИ -> КОНТЕКСТ (цель, описание, проект, ограничения, приоритет, критерии)
          |
          v
MANAGER — ЦЕНТРАЛЬНЫЙ ОРКЕСТРАТОР
   +--> ANALYST     требования, сценарии, критерии приёмки
   +--> ARCHITECT   архитектура, зависимости, технические решения
   +--> DESIGNER    UI/UX, пользовательские потоки, состояния
   +--> CODER       реализация и исправление кода
   +--> TESTER      проверка критериев и поиск дефектов
   +--> DEVOPS      инфраструктура, CI/CD, развёртывание
   +--> COPYWRITER  тексты и документация
          |
          v
ПРОВЕРКА РЕЗУЛЬТАТОВ -> исправление / блокировка / принятый результат
          |
          v
ОБНОВЛЕНИЕ ПРОГРЕССА ПРОЕКТА
```

Это логическая карта ответственности, а не обязательная цепочка из всех специалистов для каждой задачи. Маршрут зависит от содержания задачи и доступных агентов.

## 3. Роли и границы ответственности

### 3.1. MANAGER — внутренний координатор

Получает и разбирает запрос, определяет цель, выявляет неполные требования, зависимости и риски, проверяет доступность активных агентов, назначает исполнителей, передаёт контекст и критерии готовности, проверяет полноту результатов, организует контроль качества и сообщает пользователю итог, ограничения и нерешённые вопросы. Он не должен направлять весь запрос случайному агенту.

**Передача специалисту содержит:** целевую роль и ID агента; контекст и цель этапа; входные артефакты и ссылки; зависимости; ограничения и разрешённые инструменты; критерии приёмки; ожидаемый формат результата.

Шаблон MANAGER описывает маршрутизацию и fallback для отсутствующих ролей. Реальную автоматическую диспетчеризацию нужно подтверждать кодом.

### 3.2. ANALYST — аналитик требований

Преобразует идею в проверяемую спецификацию: выясняет проблему и ожидаемое поведение, определяет граничные случаи и пользовательские сценарии, формулирует критерии приёмки, ограничения и неопределённости. Если продолжение небезопасно без ответов, возвращает вопросы MANAGER. Не меняет архитектуру самовольно и не выдаёт предположения за требования пользователя.

### 3.3. ARCHITECT — технический архитектор

Изучает существующий код и компоненты, выявляет зависимости, определяет API-контракты и структуры данных, оценивает безопасность, производительность и совместимость, фиксирует технические ограничения и передаёт CODER технические требования. Не проектирует систему в отрыве от реализации.

### 3.4. DESIGNER — специалист по UI/UX

Определяет место обнаружения функции, пользовательский путь, состояния компонентов, пустые состояния, ошибки, загрузку и блокировки, адаптивность и визуальную согласованность. Результат — описание интерфейса, компонентов, состояний и потоков.

### 3.5. CODER — исполнитель реализации

Работает по согласованным требованиям и архитектурным контрактам, изменяет необходимые компоненты, обрабатывает ошибки, добавляет или обновляет тесты, сообщает о противоречиях и возвращает изменённые артефакты, описание результата и инструкции проверки. Написанный код сам по себе не означает принятие задачи.

### 3.6. TESTER — контроль качества

Проверяет результат по критериям приёмки, выполняет релевантные позитивные и негативные тесты, ищет регрессии и проверяет обработку ошибок. В шаблоне предусмотрены вердикты `PASSED` и `REJECTED`. Отчёт включает вердикт, выполненные проверки, дефекты, шаги воспроизведения и ограничения. `PASSED` подтверждает только выполненные проверки в заявленных границах.

### 3.7. DEVOPS — инфраструктура и поставка

Подключается к задачам окружения, инфраструктуры, CI/CD, развёртывания, серверов и автоматизации поставки. Не требуется для каждой обычной задачи UI или бизнес-логики.

### 3.8. COPYWRITER — тексты и документация

Готовит тексты интерфейса, подсказки, сообщения об ошибках, документацию и материалы с заданным tone of voice, не меняя технический смысл требований ради стиля.

## 4. Карта маршрутизации задач

| Тип запроса | Основной маршрут | Дополнительные роли |
| --- | --- | --- |
| Новая функция с неясными требованиями | ANALYST → MANAGER | ARCHITECT, DESIGNER |
| Техническое изменение с ясным ТЗ | CODER → TESTER | ARCHITECT при межмодульных изменениях |
| Изменение UI | DESIGNER → CODER → TESTER | ANALYST при неясном поведении |
| Изменение архитектуры | ANALYST → ARCHITECT → CODER → TESTER | DEVOPS при изменении инфраструктуры |
| Исправление ошибки | Анализ причины → CODER → TESTER | ARCHITECT при системной причине |
| Новая интеграция | ANALYST → ARCHITECT → CODER → TESTER | DEVOPS при необходимости |
| CI/CD или развёртывание | ARCHITECT при необходимости → DEVOPS → TESTER | CODER |
| Новая документация | COPYWRITER | ANALYST, ARCHITECT |
| Комплексная задача | ANALYST → план MANAGER → профильные специалисты → TESTER | Все необходимые роли |

Маршрут не жёсткий. Опечатке не нужен ARCHITECT; изменение формата событий чата может затронуть runtime, сервер, транспорт frontend и тесты, поэтому зависимости надо выявлять заранее.

## 5. Постановка задачи внутри приложения

Минимальная структура: название; цель; текущее и желаемое поведение; проект; приоритет; ограничения; критерии приёмки; зависимости; входные материалы (файлы, ссылки, ошибки, примеры); дополнительные условия (разрешения, тесты, документация). Не все поля обязаны быть обязательными при создании. MANAGER решает, можно ли продолжить безопасно, или нужны уточнения.

```text
Получить запрос -> определить цель -> проверить контекст
 -> если данных недостаточно: сформировать вопросы и получить уточнения
 -> определить тип, масштаб, зависимости и риски
 -> сформировать критерии приёмки -> подготовить план и маршрут
```

Это целевой регламент. Форма задачи или наличие MANAGER не доказывает, что все шаги автоматизированы.

## 6. Как MANAGER формирует план выполнения

План должен быть структурой для отслеживания, а не только текстовым ответом. Каждый этап содержит уникальный ID, название и цель, назначенную роль/агента, входные данные, ожидаемый артефакт, критерии завершения, зависимости, ограничения и разрешения, состояние, результат и ссылки на артефакты.

Пример последовательного плана: ANALYST формирует требования; ARCHITECT определяет модули и контракты; DESIGNER описывает UI, если он затронут; CODER реализует и добавляет тесты; TESTER проверяет критерии; MANAGER формирует сводный отчёт. Это пример, не обязательный маршрут каждой задачи.

Правила: разбивать крупную работу на проверяемые этапы; определять входы и выходы до назначения; учитывать зависимости; не создавать бесполезные этапы; не считать отправку промпта завершением; сохранять результаты; пересматривать этапы при изменении требований; не запускать зависимые этапы преждевременно; разрешать параллельность только при подтверждённой поддержке и независимости работ. В `docs/MODULE_ARCHITECTURE.md` командное выполнение описано как последовательное; параллельность нельзя считать действующей возможностью без отдельного подтверждения реализации.

## 7. Жизненный цикл задачи

Предлагаемая унифицированная модель:

```text
DRAFT -> SUBMITTED -> ANALYSIS -> PLANNED -> IN_PROGRESS -> REVIEW -> COMPLETED
                       |              |           |           |
                       v              |           v           v
              NEEDS_CLARIFICATION <----+         BLOCKED     REWORK
                       ^                          |           |
                       +------ ANALYSIS           +-> IN_PROGRESS
                                                   +-> IN_PROGRESS
```

Можно предусмотреть терминальное состояние `CANCELLED`, если отмена поддерживается. Это предлагаемая модель проектной задачи, не текущие статусы runtime чата. `thinking`, `streaming`, `waiting_approval` и `turn_completed` относятся к ходу чата и не заменяют жизненный цикл задачи.

- `DRAFT` — создание/редактирование.
- `SUBMITTED` — передана на обработку.
- `ANALYSIS` — уточняются требования.
- `NEEDS_CLARIFICATION` — требуется ответ пользователя.
- `PLANNED` — план и критерии сформированы.
- `IN_PROGRESS` — выполняется этап.
- `BLOCKED` — нужна разблокировка.
- `REVIEW` — проверка результата.
- `REWORK` — требуется исправление.
- `COMPLETED` — обязательные критерии выполнены и результат принят по правилам приложения.
- `CANCELLED` — выполнение прекращено поддерживаемой процедурой.

Для переходов определяются инициатор, условия, обязательные данные и событие аудита.

## 8. Контроль выполнения и прогресса

Отслеживать текущий этап и агента, время начала/окончания, завершённые и ожидающие этапы, зависимости, ошибки, запросы подтверждения, причины блокировок, попытки исправления, тесты и оставшиеся критерии.

Правила: этап завершается только с ожидаемым результатом; результат сопоставляется с критериями; ошибка агента не означает успех; блокировка содержит причину и следующее действие; частичный результат нельзя выдавать за полный; попытки связаны с предыдущими результатами; после исправлений проверяются затронутые критерии; прогресс рассчитывается по этапам и критериям, а не длине диалога.

Отчёт MANAGER: что требовалось, что сделано, завершённые этапы, выполненные и невыполненные проверки, блокировки и причины, оставшиеся критерии и следующее действие.

## 9. Контроль качества и возврат на исправление

```text
CODER возвращает результат -> MANAGER проверяет артефакты -> TESTER проверяет критерии
  REJECTED -> баг-репорт с доказательствами -> исправление CODER -> повторная проверка
  PASSED   -> MANAGER формирует итог
```

Баг-репорт содержит ID задачи и этапа, проблему, ожидаемое и фактическое поведение, шаги воспроизведения, окружение и входные данные, серьёзность/приоритет, невыполненный критерий и подтверждающие логи/тесты. Если TESTER отсутствует, MANAGER может провести базовую проверку, но должен сообщить, что независимая проверка не выполнялась.

## 10. План развития проекта и связь задач с целями

Иерархия: цели проекта → направления развития → milestones → эпики/крупные функции → задачи → этапы выполнения → артефакты и проверки.

Рекомендуемые сущности:
- **Project Goal:** ожидаемое изменение продукта, измеримый результат, критерии, приоритет.
- **Milestone:** этап развития, связанные цели и задачи, условия закрытия.
- **Epic:** крупная функциональная область, связанные задачи, зависимости и критерии.
- **Task:** конкретная работа, ответственный агент, план, статус, критерии и результат.
- **Execution Step:** шаг, роль, входы/выходы, статус и результат проверки.

План формируют от желаемого состояния продукта, затем разбивают на направления, проверяемые результаты, этапы и зависимости, эпики и задачи, критерии готовности и порядок выполнения. План пересматривается при изменении требований или технических ограничений. MANAGER может рекомендовать декомпозицию, но изменение целей и приоритетов должно отражаться в истории и, когда предусмотрено, подтверждаться пользователем.

Наличие проектов и задач в UI не доказывает наличие полноценного планировщика, milestones, зависимостей или автоматического пересчёта прогресса: каждый механизм проверяется отдельно.

## 11. Контекст и передача результатов между агентами

Контекст этапа включает исходную задачу, цель проекта, актуальные требования и критерии, архитектурные ограничения, результаты предыдущих этапов, относящиеся файлы/ссылки, разрешения, известные дефекты и формат результата.

Рекомендуемая логическая структура артефакта:

```text
task_id, step_id, agent_id, input_context, output_artifact,
acceptance_criteria, status, errors, verification_result,
created_at, completed_at
```

Фактические поля должны соответствовать модели данных. В `docs/MODULE_ARCHITECTURE.md` указано, что командное выполнение сохраняет вывод этапов, модель и количество вызовов инструментов в истории задачи; это нужно сверить со схемой хранения и кодом. Передача пути проекта как метаданных не означает автоматического включения всех файлов по этому пути: содержимое нужного файла должно быть предоставлено поддерживаемым механизмом.

## 12. Инструменты, разрешения и подтверждения

Назначение агента не даёт права на все действия. Перед операцией проверяются доступность инструмента, разрешение конкретного агента, разрешённые пути, глобально включённый доступ, необходимость подтверждения, ограничения размера/типа файлов и побочные эффекты.

Правила безопасности:
1. Не выдавать лишние разрешения.
2. Не обходить проверки путей.
3. Не запускать скачанный внешний код автоматически.
4. Не считать ответ модели доказательством успешного вызова инструмента.
5. Различать запрос подтверждения и подтверждённое действие.
6. При отказе сообщать, что заблокировано.
7. Не объявлять опасную операцию выполненной без фактического результата.

Документация инструментов указывает файловые операции, ограничения доступа и отдельное разрешение на удаление. Полноценная изоляция на уровне ОС не гарантируется.

## 13. Runtime чата и управление проектной задачей — разные уровни

### Уровень A: ход чата агента

- `chat/agent_runtime.py` — ход выполнения, контекст, вызовы инструментов и статусы.
- `chat/conversation_store.py` — журнал событий.
- `chat/chat_events.py` — доставка событий.
- `chat/provider_adapter.py` — адаптер провайдера.
- `agent_tools.py` — инструменты.
- `server.py` — HTTP API.
- `frontend/chat-transport.js` — потоковая доставка в браузер.
- `frontend/chat-renderer.js` — отображение событий.

```text
AgentRuntime -> ConversationStore (запись) -> EventHub -> HTTP SSE
             -> ChatTransport -> ChatRenderer
```

Для чата используются `sequence`, `epoch`, `command_id`, `tool_call`, `tool_result`, `approval_required`, `approval_resolved`, `turn_completed`.

### Уровень B: выполнение проектной задачи

Отвечает за цель, утверждённый план, ответственных за этапы, фактический прогресс, блокировки, пройденные критерии и решение о завершении. `turn_completed` не означает принятие проектной задачи. Нужно проверить, как сущности задач и командное выполнение связаны с runtime чата и как результат этапа попадает в общий статус задачи.

## 14. Обработка исключений и fallback

- **Агент отсутствует/неактивен:** MANAGER выполняет базовую функцию или выбирает доступную замену; фиксирует отсутствующую роль, исполнителя и ограничения качества. Не заявляет независимую проверку, если TESTER отсутствовал.
- **Противоречивые требования:** не выбирать молча; передать MANAGER, уточнить у пользователя, не выполнять необратимые действия до разрешения конфликта.
- **Ошибка инструмента:** сохранить ошибку, оценить безопасный повтор, не повторять побочный эффект вслепую; при невозможности продолжить — блокировка или фактический статус ошибки.
- **Отклонённая проверка:** баг-репорт, связь с критериями, исправление и повторная проверка.
- **Изменение требований:** зафиксировать изменение, определить затронутые этапы и артефакты, пересмотреть зависимости.
- **Отмена:** различать отмену хода модели, вызова инструмента, этапа и всей задачи. Наличие `cancel_task` в chat runtime не доказывает отмену на всех уровнях.

## 15. История, аудит и прозрачность

Для каждой задачи рекомендуется хранить исходный запрос и уточнения, план и его изменения, назначения агентов, входы/выходы этапов, результаты инструментов, решения о подтверждении, ошибки и повторы, тестовые результаты, финальный статус и основание завершения/блокировки.

История должна позволять восстановить, почему выбран маршрут, кто выполнил этап и почему результат признан успешным. Отдельно определяются срок хранения, редактирование секретов и действия, требующие аудита.

## 16. Минимальные критерии приёмки внутренней системы управления

1. Пользователь создаёт задачу с полными требованиями.
2. MANAGER выявляет неполноту и запрашивает уточнение.
3. Формируется план с проверяемыми этапами.
4. Задача назначается подходящим активным агентам.
5. Исполнители получают результаты предыдущих этапов.
6. Отсутствие профильного агента обрабатывается предсказуемо.
7. Результат этапа сохраняется и связан с задачей.
8. Ошибка инструмента не маскируется под успех.
9. Отклонённая проверка ведёт к исправлению и повторной проверке.
10. Блокировка содержит причину и следующее действие.
11. Отмена не оставляет задачу ложно завершённой.
12. Статус задачи согласуется с обязательными этапами.
13. Прогресс отражает реальные результаты.
14. История позволяет проследить выполнение.
15. Пользователь видит завершённое, непроверенное и требующее решения.

## 17. Какие файлы проекта определяют внутренний процесс

Основные точки аудита:
- `agents/templates/MANAGER.md` — оркестрация и маршрутизация.
- `agents/templates/ANALYST.md` — требования.
- `agents/templates/ARCHITECT.md` — техническое проектирование.
- `agents/templates/DESIGNER.md` — UI/UX.
- `agents/templates/CODER.md` — реализация.
- `agents/templates/TESTER.md` — качество.
- `agents/templates/DEVOPS.md` — инфраструктура.
- `agents/templates/COPYWRITER.md` — тексты и документация.
- `docs/MODULE_ARCHITECTURE.md` — модули, разрешения, командное выполнение.
- `docs/ai-context/01-architecture.md` — слои и потоки данных.
- `docs/ai-context/modules/agent-runtime.md` — runtime хода чата.
- `docs/ai-context/modules/agent-tools.md` — инструменты и границы доступа.
- `docs/ai-context/modules/server-api.md` — API и серверная интеграция.
- `docs/ai-context/modules/frontend-chat.md` — транспорт и события UI.
- `docs/ai-context/tests/test-map.md` — карта тестов.

`AGENTS.md` регулирует работу над репозиторием. Правила GitHub нельзя путать с внутренней маршрутизацией задач между агентами приложения.

## 18. Порядок технического аудита перед признанием схемы реализованной

Для каждого элемента: найти документ/шаблон; найти реализацию; найти тесты переходов и ограничений; записать статус: «подтверждено», «частично реализовано», «не подтверждено» или «требует реализации».

В первую очередь проверить:
- как MANAGER вызывает других агентов;
- где хранится план задачи;
- какие сущности связывают проект, задачу и этап;
- как рассчитывается прогресс;
- как передаются результаты;
- как TESTER связан с завершением;
- как работают повторы, блокировки и отмена;
- какие действия требуют подтверждения;
- как результаты командного выполнения сохраняются и отображаются в UI.

## Итоговый принцип

MANAGER управляет маршрутом и ходом задачи; профильные агенты отвечают за специализированные результаты; TESTER проверяет критерии; история фиксирует фактические действия; состояние проекта отражает реальное продвижение к целям. Любой автоматический переход, механизм планирования или гарантия должны подтверждаться реализацией и тестами, а не только системными инструкциями агентов.
